# Atlas of Fins｜開發方法

這個專案的長期目標不是每個版本重新發明玩法，而是用成熟系統穩定生產新海域、魚類與連續主線。因此開發工具必須先判斷工作類型，不再預設每次都建立多個 Slice。

## 1. 兩種工作模式

### A. 海域＋章節內容包（預設）

適用於新增海域、魚類、釣場、港口、NPC、觀察、研究、事件、主線或固定日誌頁。

一個內容包包含：

```text
前章承接
→ 海域身份與生態規則
→ 魚類／釣點／觀察／研究資料
→ NPC 場景與章節事件
→ 固定主線日誌頁
→ 後章鉤子
→ 內容驗證、存檔重載與瀏覽器流程
```

魚類與釣場可以先建立資料骨架，但海域完成前必須補齊同章 NPC、故事事件與日誌，避免事後硬插劇情造成條件不合。

### B. 共用引擎變更（例外）

只有以下情況才使用工程 Slice：

- 修改存檔版本或遷移策略。
- 改變跨系統事件、經濟、航行、釣魚或 UI 架構。
- 多個相依風險無法在一次可驗證改動中安全完成。
- 需要分階段保持每個 checkpoint 都能正常遊玩。

design rule 或純內容修正不會自動成為下一版本，也不應為了套流程虛構 `Slice A`。

## 2. 海域內容包的最小規格

每片海域只維護一份短規格，建議包含：

| 區塊 | 必要內容 |
|---|---|
| 身份 | 海域名稱、色彩、洋流、水溫、主要棲地與情緒 |
| 航線 | 從哪裡來、如何返回、解鎖條件、航程與停泊點 |
| 玩法 | 釣點、魚池、時段／天氣偏好、觀察、研究與區域事件 |
| 生態 | 魚種來源、棲地與尺寸合理性、單一海域歸屬、稀有以上魚類固定日誌頁；數量與等級規則引用 `GAME_DESIGN.md` |
| 敘事 | 前章承接、主要 NPC、4～6 個短場景、章節事件、後章鉤子 |
| 日誌 | 該海域固定頁 ID、順序、解鎖事件、標題、內文與收尾 |
| 驗收 | 內容參照、一般流程、開發者定位、存檔重載、窄螢幕與例外 |

主線內容只在 [MAIN_STORY.md](MAIN_STORY.md) 管理；海域規格引用章節 ID，不另外複製世界主線全文。

## 3. 建議實作順序

1. 讀 `GAME_DESIGN.md`、`MAIN_STORY.md` 對應章節與 `CURRENT.md`。
2. 先寫清楚前章留下什麼、此章改變什麼、要把什麼交給下一章。
3. 建立資料 ID 與內容參照，先讓驗證器能檢查缺漏與重複。
4. 完成海域硬內容：地點、魚類、魚池、航線、觀察與研究。
5. 接上 NPC 場景、主線事件與固定日誌頁；日誌不自行創造進度。
6. 做最小 UI 接入與開發者定位，避免另建只為測試而存在的玩法入口。
7. 跑內容驗證、單元測試、舊存檔重載、Chromium 完整流程與必要壓測。
8. 只更新 `CURRENT.md`；版本結束後才把該版本計畫與報告凍結到 `versions/`。

## 4. 版本連貫規則

每章固定回答五個問題：

1. 玩家從上一海域帶著哪一個認知或物件而來？
2. 本海域第一次讓玩家理解什麼新的海洋關係？
3. 主要 NPC 如何讓這個理解變得具體？
4. 本章完成後，船屋或海圖留下什麼永久痕跡？
5. 哪一條自然線索指向下一海域？

前後章以「一條主要承接」為原則，不同時堆疊多個中央謎題。已解鎖海域保持自由往返，後章不能讓前章 NPC 跨海追蹤玩家。

## 5. 存檔與資料原則

- 新內容使用穩定唯一 ID；文字、順序與解鎖對應放在資料目錄，不寫死在 UI。
- 單純新增魚、海域或固定日誌頁通常不需提高存檔版本；只有舊狀態無法安全正規化時才遷移。
- 更新前保留原始備份；一般與開發者存檔完全隔離。
- 自動／離線來源不能發現稀有以上魚類、推進主線或產生日誌解鎖。
- 今日潮記由航海日推導，不寫入歷史；固定頁只保存已讀／未讀狀態。
- 每種魚必須保存 80～120 的 `appearanceWeight`；同級魚池最高／最低原則上不超過 1.5 倍，兩種以上的魚池不可全部相同。常見、少見以海域共享，資料釣點作為原生偏好；稀有以上仍由釣點限定。
- 每個釣點至少需要一種稀有以上魚並遵守高階單點種類上限；新增高階等級只瓜分固定 6%，不得改動常見 60%、少見 30% 或未吞餌 4%。調整前後都要同步 `FISH_CATALOG.md` 並通過內容驗證。

## 6. 驗收強度按風險調整

| 改動 | 最少驗證 |
|---|---|
| 原創文字或固定資料 | 內容驗證＋相關單元測試 |
| 新魚／釣點／NPC／日誌頁 | 上述＋存檔重載＋一條瀏覽器流程 |
| 完整新海域 | 上述＋往返航線＋窄螢幕＋未捕捉例外 |
| 共用系統或存檔 | 完整單元＋所有固定存檔＋完整 Chromium＋針對性壓測 |

不要把所有歷史測試與文件檢查都設為每個小改動的硬門檻。完整回歸留給共用系統、海域完成或版本收尾。

## 7. 文件更新邊界

- 永久玩法變更：更新 `GAME_DESIGN.md`。
- 主線、NPC 弧線或章節日誌變更：更新 `MAIN_STORY.md`。
- 開發方法變更：更新本文件。
- 完成狀態與下一步：替換 `CURRENT.md` 的相關段落。
- 魚種新增、刪除或調整機率與出現條件：同步 `FISH_CATALOG.md`；該檔只反映目前魚池，不定義玩法規則。
- 歷史版本、封存提案與舊測試清單：不主動同步。
